When establishing how someone else's tool behaves, the authority order is
**vendor documentation > the shipped artifact (binary/strings/schema) > prior knowledge**.
Go to the docs first; use the binary to check the docs; never answer from memory alone.

This is the **inverse** of the standing rule in `~/.claude/CLAUDE.md` — *"verify a doc claim
against the filesystem or the host, never against another document"* — which remains correct
for **Costin's own projects**, where a doc is a claim about a machine he controls and the
machine is the ground truth. For a third-party tool the vendor's doc is not a sibling
document, it is the specification; the binary is only its compiled consequence and can be
misread.

**Why:** measured on 2026-09-07 in the rite session. The question was which shell Claude Code
uses for hooks on Windows. Three answers, in order:
1. Prior knowledge → `.sh` + `.bat`. **Wrong** — `cmd.exe` is never the hook shell.
2. Binary strings (205 MB ELF) → one `.sh`, Git Bash mandatory. **Closer, still wrong** — it
   over-read an error string and treated Git for Windows as required.
3. Official docs → `.sh` + `.ps1`; Git for Windows optional; PowerShell is the fallback; and
   hooks have an **exec form** (`args` set) that bypasses the shell entirely — a capability
   invisible in both earlier sources.

Each escalation overturned the one before. Costin had to explicitly say *"please spend some
tokens on web search"* to get to the correct answer.

**How to apply:** when a question is about Claude Code, an OS, or any third-party dependency —
fetch the vendor docs before answering, and say plainly which of the three levels an answer
came from. State "documentation plus binary strings, not a test" rather than presenting it as
verified. Do not wait to be told to search.

Two halves of one discipline, both paid for on 2026-09-12 while measuring rite's `legacy_layout`
against a `docs-yaml` fixture.

**Keep the variable OUT of the tree under test.** To compare "declared" against "undeclared" I
moved `.rite.yaml` aside as `off.yaml` — *inside the fixture directory*. That stray root-level
YAML then counted as source, so the baseline run described a project with source code and the
comparison run described a documents-only one. An unexplained GREEN→NA appeared and cost several
minutes of hunting a bug in the feature. Park the toggled file in a sibling directory, or delete
and rewrite it; never rename it in place.

**Why:** the thing being toggled is usually a marker, config or dotfile, which is exactly the
class of file tools scan for. Renaming it does not remove it from the scan — it changes what the
scan sees. This is the same failure as rite's own plan-attribution contamination, where the
session building the attributor ran `ls ~/.claude/plans/` and thereby made its own transcript
mention every plan on the machine. **The act of measuring changed what was measured**, twice, in
one repository.

**Diff the FINDINGS, not the summary line.** The first implementation of the feature looked like
an improvement by its totals and was silently destroying three true GREEN findings. `27 YELLOW →
17 YELLOW` says nothing about *which* findings moved or what was lost on the other rows. Dump
both verdicts to files, one finding per line, and `diff` them — then every row that changed has
to be explained out loud before the change is accepted.

**How to apply:** before trusting any before/after measurement — (1) put the variable outside the
tree, (2) capture full per-finding output on both sides, (3) diff them, (4) account for every
changed line, including ones that got *better*. An unexplained improvement is as much a signal as
an unexplained regression.

## feedback_never_edit_files_through_heredocs.md · type: feedback

description: "Multi-line Python that edits files goes to a script FILE and is then run — never a bash heredoc. And verify a file survived with a byte count, never a parse."
metadata: 
  node_type: memory

  originSessionId: 3dce68ee-94ba-4676-8bc7-078931660f46

---

**Write the script to a file, then run it. Never pipe multi-line editing code through a
heredoc.**

On 2026-09-09 this destroyed a source file. A `python3 - <<'PYEOF'` block containing
`p.write_text(s, encoding="utf-8", newline="\n")` had its backslash-n mangled by shell quoting
into a *literal* backslash-n. `write_text` opens the file for writing — **which truncates it** —
and only then validates the `newline` argument and raises. `scripts/rite-check.py` was left at
**zero bytes**. It happened a second time in the same session, appending a literal `\n` to a
YAML file.

**Why:** it fails silently and destructively. The traceback points at the write, not at the
quoting, so the cause is invisible in the command you just ran. A file that gets written to a
path *is* the risk; there is no partial-failure mode.

**How to apply:**
- Multi-line edits → `Write` the script to the scratchpad, then `python3 <path>`. No quoting
  layer, and the script is re-readable when it goes wrong.
- Single-line `sed`/`grep` in Bash is fine. The trap is multi-line Python with escapes.
- Prefer the `Edit` tool for exact-match replacements in a known file — no escaping at all.

**Verify survival with a byte or line count — never a parse.** After that failure I checked with
`ast.parse` (reported "parses OK") and `grep -c` (returned 0) and concluded the file was intact.
**Both are exactly what an empty file produces.** Two green signals on a destroyed file. Use
`wc -l`, `wc -c`, or `git diff --stat`.

Same family: never pass log or prose text through a shell either — backticks get executed. That
one ate words out of two committed LOG entries the same day.

## feedback_never_git_checkout_to_undo_an_experiment.md · type: feedback

---
name: feedback-never-git-checkout-to-undo-an-experiment
description: "To undo a deliberate temporary break, back up to a file and restore with cp — never `git checkout <file>`, which reverts to HEAD and destroys uncommitted work"
metadata: 
  node_type: memory
  type: feedback
  originSessionId: c8b2dde8-3b9d-4989-b69d-1dcc14d64f7d
  modified: 2026-09-10T07:29:09.188Z
---

When deliberately breaking a file to prove a test fails, **back it up to a real file first and
restore it with `cp`.** Never use `git checkout <file>` to undo the break.

**Why:** `git checkout <file>` reverts to HEAD, not to "before my last edit". On 2026-09-10 I
used it to undo a two-line experimental break in `scripts/rite-check.py` and it silently
discarded three completed, uncommitted edits — a whole feature I had just finished and verified.
Redoing it cost real time, and only worked because the content was still in conversation
context. It would not have been recoverable in a fresh session.

**How to apply:** the safe form, which also gives a verifiable restore:

```bash
cp target.py "$SCRATCHPAD/target.py.bak"      # byte count printed
# ...break it, run the test, watch it fail...
cp "$SCRATCHPAD/target.py.bak" target.py      # byte count must match
```

The general rule: **never reach for a command whose scope is wider than the change you are
undoing.** `git checkout`, `git reset --hard`, `git clean` all operate on tracked state as a
whole, not on your last action.

Same family as [[feedback-never-edit-files-through-heredocs]] — a tool doing more than intended,
destroying a file, with no error to signal it. Both are cases where the verification step itself
caused the damage.

## feedback_shell_edits_damage_quietly.md · type: feedback

description: "sed and heredocs edit files without reporting damage; verify by reading back, and prefer a Python script that asserts its match count"

  originSessionId: 3351be49-6648-4e40-a79e-79f266f73aa3

---

Shell one-liners that edit files here have twice succeeded loudly and damaged quietly.

- **2026-09-09** — a `python3 - <<'PYEOF'` heredoc truncated a source file to zero bytes
  ([[feedback-never-edit-files-through-heredocs]]).
- **2026-09-10** — `sed -i 's|…|…|'` using `|` as *both* the delimiter and a regex alternation
  replaced a whole comment line in `hooks/rite.sh` with the literal `X`. sed exited 0 and
  printed nothing. Found only by reading the file afterwards.

**Why:** `sed -i` has no concept of "expected number of matches". A pattern that matches
nothing, or matches the wrong thing, is indistinguishable from success at the exit code. The
damage surfaces later, in a file nobody re-reads, which is the same failure mode as the doc rot
[[rite]] exists to attack — one level down, in the tooling.

- **2026-09-10** — a *restore* that verified clean still failed. After break-testing a gate,
  `cp` put back a byte-identical file and the test kept failing: Python invalidates `__pycache__`
  on `(mtime, size)`, and the copy landed in the same second with the same size, so a stale
  `.pyc` was still being imported. The byte count said restored; the cache was the liar.
  **After restoring any module another script imports, `rm -rf __pycache__`.**

**How to apply:** for anything beyond a single unambiguous substitution, write a Python script
to the scratchpad and run it, with `if text.count(old) != 1: sys.exit("ABORT")` before writing
and a byte count printed after. That pattern caught several mis-targeted edits during the
2026-09-10 sessions before they landed. When `sed -i` is genuinely the right tool, pick a
delimiter that cannot appear in the pattern, and `grep` the result back — never trust the exit
code alone.

Script: `~/projects/claude-run/claude-plugin-probe-20260908.sh`
(candidate to graduate to `~/projects/bin/` if used more than twice).

```bash
claude-plugin-probe-20260908.sh <marketplace-path> <plugin-name>   # install + diff
claude-plugin-probe-20260908.sh --off <plugin-name> [<market>]     # reverse + diff back
claude-plugin-probe-20260908.sh --snapshot                         # capture only
```

**The insight it encodes: reversing a plugin install is easy — `claude plugin disable <name>`
is built in. Noticing what it DID is the hard part.** A plugin can shadow an existing slash
command silently; you find out days later when a command stops behaving as it used to, having
half-learned the new behaviour. So the tool is a probe, not an installer: snapshot → install →
snapshot → diff. It reports and never judges, because what to do about a collision is a
decision, not a script's business.

**What it captures on each side:** `~/.claude/settings.json` (structural JSON diff, not a text
diff), `claude plugin list`, `claude plugin marketplace list`, and the `~/.claude/commands/`
inventory. After install it also runs `claude plugin details <name>` — the component inventory
the harness actually resolved, which is the collision evidence.

**Collision detection runs BEFORE the install**, comparing plugin `skills/<name>/SKILL.md`
directory names against `~/.claude/commands/*.md`. Proven on 2026-09-08: it flagged `log` and
`preflight` as colliding with Costin's own commands before anything was installed.

**Two things it cannot test from outside a session, and says so:** whether the commands appear
in the `/` menu and under what names, and which one a colliding bare name actually resolves to.
The docs are self-contradictory on precedence — they say both "the skill takes precedence" and
"the bare name also works unless another command uses it" — so it must be observed, not derived.

**ANSWERED 2026-09-08, in a live session: plugin skills are NAMESPACED and never shadow.** The
`/` menu showed `/rite:log`, `/rite:preflight`, `/rite:handoff`, `/rite:end` — no bare names —
alongside Costin's own `/log` and `/preflight`, untouched. So a name collision between a plugin
skill and a personal command is not a real risk, and the pre-install collision check is a
false-alarm generator rather than a safety net. `disable-model-invocation: true` behaves as
documented: those skills are hidden from the model's skill listing while still offered to the
user in the menu.

**Iterating on a locally-sourced plugin: the working tree is NOT what runs.** The install cache
(`~/.claude/plugins/cache/<market>/<plugin>/<version>/`) is a real copy, not a symlink, and
`claude plugin update` is version-gated — it answers "already at the latest version" against
edited source and does nothing. **Bump `.claude-plugin/plugin.json` `version` before every
`update`, or you are testing the previous install.** Verified the hard way: a correct fix
appeared not to work for several minutes because the cache still held the bug.

**`claude plugin install` dropped `effortLevel` from `settings.json` (08-09); `update` did not.**
Treat them as different operations and snapshot settings before `install` specifically.

**`update` succeeds and the RUNNING session keeps the old code.** It prints "Restart to apply
changes" and means it: verified twice on 2026-09-12, going 0.22.0 → 0.23.0 → 0.24.0 while the
session that triggered each update carried on with the previously loaded hooks. So testing a
plugin change in the session that installed it measures the PREVIOUS version — reload the window
first. Pairs with the version-gating trap above: bump, update, restart, then test.

**It is not only hooks — SKILL BODIES are served pre-edit too.** Observed 2026-09-12 at 0.25.0:
`/rite:end` was invoked in the session that had just edited `skills/end/SKILL.md`, and the
harness handed over the OLD body — the newly added block was simply absent, with no warning and
nothing in the output to suggest a stale copy. **A skill edit therefore cannot be tested in the
session that made it, and the failure mode is silent omission rather than an error.** This is the
harder half of the same trap: a hook that does not fire is at least suspicious, whereas a prompt
that is quietly one revision old reads as a correct prompt. Restart, then invoke, then check that
the specific new text is actually present before believing any result about it.

**Rite's marketplace is a DIRECTORY source** (`~/.claude/plugins/known_marketplaces.json` →
`{"source": "directory", "path": "/home/perieteanu/projects/rite"}`), so `update` reads the local
working tree and needs no push to GitHub. `installed_plugins.json` records a `gitCommitSha`
alongside the version, so commit before updating if you want that field to mean anything.

**A hook that logs `success` may have done nothing.** The harness reads
`hookSpecificOutput.additionalContext`; a top-level `additionalContext` is ignored, and the hook
is still logged as `success`. The proof is a second debug line the working hooks emit and the
broken one does not: `Hook SessionStart (<cmd>) provided additionalContext (N chars)`. Grep the
extension log for that line — its ABSENCE is the signal. Log path:
`~/.config/Code/logs/<stamp>/window1/exthost/Anthropic.claude-code/Claude VSCode.log`.

**Useful CLI facts:** there is no `claude plugin validate`; `marketplace add` is the only way to
load a manifest, and it writes to `~/.claude`. `claude plugin details <name>` shows a resolved
component inventory and projected token cost. Under `entrypoint=claude-vscode` the `/plugin`
TUI is unavailable, so install and removal go through the `claude` shell CLI.
