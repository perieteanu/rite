## feedback_authority_ranking_for_third_party_tools.md · type: feedback

---
name: feedback-authority-ranking-for-third-party-tools
description: For third-party tool behaviour, vendor docs outrank the shipped binary, which outranks Claude's prior knowledge — the inverse of the rule for Costin's own projects
metadata:
  type: feedback
---

When establishing how someone else's tool behaves, the authority order is
**vendor documentation > the shipped artifact (binary/strings/schema) > prior knowledge**.
Go to the docs first; use the binary to check the docs; never answer from memory alone.

This is the **inverse** of the standing rule in `~/.claude/CLAUDE.md` — *"verify a doc claim
against the filesystem or the host, never against another document"* — which remains correct
for **Costin's own projects**, where a doc is a claim about a machine he controls and the
machine is the ground truth. For a third-party tool the vendor's doc is not a sibling
document, it is the specification; the binary is only its compiled consequence and can be
misread.

**Why:** measured on 2026-09-07 in the rite session. The question was which shell Claude Code
uses for hooks on Windows. Three answers, in order:
1. Prior knowledge → `.sh` + `.bat`. **Wrong** — `cmd.exe` is never the hook shell.
2. Binary strings (205 MB ELF) → one `.sh`, Git Bash mandatory. **Closer, still wrong** — it
   over-read an error string and treated Git for Windows as required.
3. Official docs → `.sh` + `.ps1`; Git for Windows optional; PowerShell is the fallback; and
   hooks have an **exec form** (`args` set) that bypasses the shell entirely — a capability
   invisible in both earlier sources.

Each escalation overturned the one before. Costin had to explicitly say *"please spend some
tokens on web search"* to get to the correct answer.

**How to apply:** when a question is about Claude Code, an OS, or any third-party dependency —
fetch the vendor docs before answering, and say plainly which of the three levels an answer
came from. State "documentation plus binary strings, not a test" rather than presenting it as
verified. Do not wait to be told to search.

## reference_plugin_install_probe.md · type: reference

name: reference-plugin-install-probe
description: How to install a near-mature Claude Code plugin safely — snapshot, install, diff. The risk is invisibility, not irreversibility.
metadata:
  type: reference
---

Script: `~/projects/claude-run/claude-plugin-probe-20260908.sh`
(candidate to graduate to `~/projects/bin/` if used more than twice).

```bash
claude-plugin-probe-20260908.sh <marketplace-path> <plugin-name>   # install + diff
claude-plugin-probe-20260908.sh --off <plugin-name> [<market>]     # reverse + diff back
claude-plugin-probe-20260908.sh --snapshot                         # capture only
```

**The insight it encodes: reversing a plugin install is easy — `claude plugin disable <name>`
is built in. Noticing what it DID is the hard part.** A plugin can shadow an existing slash
command silently; you find out days later when a command stops behaving as it used to, having
half-learned the new behaviour. So the tool is a probe, not an installer: snapshot → install →
snapshot → diff. It reports and never judges, because what to do about a collision is a
decision, not a script's business.

**What it captures on each side:** `~/.claude/settings.json` (structural JSON diff, not a text
diff), `claude plugin list`, `claude plugin marketplace list`, and the `~/.claude/commands/`
inventory. After install it also runs `claude plugin details <name>` — the component inventory
the harness actually resolved, which is the collision evidence.

**Collision detection runs BEFORE the install**, comparing plugin `skills/<name>/SKILL.md`
directory names against `~/.claude/commands/*.md`. Proven on 2026-09-08: it flagged `log` and
`preflight` as colliding with Costin's own commands before anything was installed.

**Two things it cannot test from outside a session, and says so:** whether the commands appear
in the `/` menu and under what names, and which one a colliding bare name actually resolves to.
The docs are self-contradictory on precedence — they say both "the skill takes precedence" and
"the bare name also works unless another command uses it" — so it must be observed, not derived.

**ANSWERED 2026-09-08, in a live session: plugin skills are NAMESPACED and never shadow.** The
`/` menu showed `/rite:log`, `/rite:preflight`, `/rite:handoff`, `/rite:end` — no bare names —
alongside Costin's own `/log` and `/preflight`, untouched. So a name collision between a plugin
skill and a personal command is not a real risk, and the pre-install collision check is a
false-alarm generator rather than a safety net. `disable-model-invocation: true` behaves as
documented: those skills are hidden from the model's skill listing while still offered to the
user in the menu.

**Iterating on a locally-sourced plugin: the working tree is NOT what runs.** The install cache
(`~/.claude/plugins/cache/<market>/<plugin>/<version>/`) is a real copy, not a symlink, and
`claude plugin update` is version-gated — it answers "already at the latest version" against
edited source and does nothing. **Bump `.claude-plugin/plugin.json` `version` before every
`update`, or you are testing the previous install.** Verified the hard way: a correct fix
appeared not to work for several minutes because the cache still held the bug.

**`claude plugin install` dropped `effortLevel` from `settings.json` (08-09); `update` did not.**
Treat them as different operations and snapshot settings before `install` specifically.

**A hook that logs `success` may have done nothing.** The harness reads
`hookSpecificOutput.additionalContext`; a top-level `additionalContext` is ignored, and the hook
is still logged as `success`. The proof is a second debug line the working hooks emit and the
broken one does not: `Hook SessionStart (<cmd>) provided additionalContext (N chars)`. Grep the
extension log for that line — its ABSENCE is the signal. Log path:
`~/.config/Code/logs/<stamp>/window1/exthost/Anthropic.claude-code/Claude VSCode.log`.

**Useful CLI facts:** there is no `claude plugin validate`; `marketplace add` is the only way to
load a manifest, and it writes to `~/.claude`. `claude plugin details <name>` shows a resolved
component inventory and projected token cost. Under `entrypoint=claude-vscode` the `/plugin`
TUI is unavailable, so install and removal go through the `claude` shell CLI.
